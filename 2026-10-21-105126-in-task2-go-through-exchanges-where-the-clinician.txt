> in prod, theres still risk of false negatives or false positives. how can we

● You can't get both error rates to zero, so the aim is to keep missed Urgent
  cases as close to zero as possible and make false alarms cheap. Here are the
  layers I'd use.

  1. Make false alarms cheap so you can afford many

  - Route each level differently. Urgent pages someone with a same-day deadline.
    Routine goes into a queue that's reviewed daily. A false Routine then costs
    someone a few seconds, which lets you set the Routine bar low.
  - Make dismissing easy. Give staff a one-click "not needed" button with an
    optional reason. That keeps review time down, and the dismissals become
    labelled data.
  - Group alerts per user. Several flags from the same person in one day should
    show up as one item with full context, not five separate alerts.

  2. Several independent checks for Urgent

  Escalate if any of these fires:
  - The bot's own human_needed field.
  - The judge.
  - A cheap keyword and pattern check that catches as much as possible: death,
    harm, "better off without", giving things away, "can't keep myself safe",
    and versions in other languages and slang.
  - Repeated judge runs, or two different models. Escalate if any run says
    Urgent. Disagreement between runs is itself a sign of uncertainty, so send
    those cases to Urgent.

  The checks fail in different ways (the keyword check misses PB03-style
  indirect signs; the LLM may "explain away" a figure of speech), so combining
  them with OR lowers the miss rate.

  3. Give the judge more context

  - The conversation, not just one message. Many risk signs build up across
    messages ("giving things away" on Monday, "won't need it" on Thursday).
    Score a rolling window of the user's recent history.
  - Context about the user, if consent allows. A recent wellbeing-tracker drop
    or missed sessions should lower the threshold for that person.
  - Let the judge say it's unsure. Add a confidence field or an "UNSURE" verdict
    that goes to a human. This beats forcing a guess.

  4. Make the bot's reply safe even when detection misses

  Missed cases become far less harmful if the reply itself is safe:
  - When there's any doubt, the bot asks one direct, caring question ("When you
    say you won't need things much longer, what do you mean?") before answering
    the surface question.
  - Crisis resources are always one tap away, with a real link instead of
    [crisis resources page].
  - The bot never closes off options in sensitive cases: no "it's fine to quit",
    no scripts for leaving.

  5. Find the misses you can't otherwise see

  False alarms show up as staff complaints. Missed cases stay silent, so you
  have to go looking for them:
  - Sample the "No" verdicts at random each week (say 2 to 5%, plus every
    message containing risk-adjacent words). The clinician labels them, and
    every miss becomes a new test row.
  - Look back after any serious incident. Check whether the system saw earlier
    signs.
  - Check facilitator reports. When a facilitator raises a concern, check
    whether the bots saw the same user beforehand.

  6. Treat the eval as a gate before each release

  - Keep a held-out set labelled by the clinician and grow it from production
    samples. Keep a separate red-team set: slang, sarcasm, emoji, other
    languages, signs buried in other questions, coercion by someone else, risk
    to others.
  - Set targets before you deploy. For example: Urgent recall ≥ 98% on the
    held-out set, with a ceiling on the false Routine rate that matches staff
    capacity.
  - Re-run the full suite on every change to a prompt or model, including
    provider model updates. Block the release if Urgent recall drops.

  7. Fail safe when something breaks

  - If the judge times out, errors, or returns JSON that doesn't parse, escalate
    by default. Don't silently pass the message through.
  - Cover nights and weekends for Urgent alerts, or tell users clearly that the
    bot isn't watched in real time and show crisis resources up front.
  - Log every verdict with the prompt and model version so you can trace any
    miss.

  In short: use several checks combined with OR, look at whole conversations,
  route cheaply, keep replies safe when a check misses, and actively sample the
  No verdicts. The sampling loop is what keeps the system improving after
  launch. Without it you'll only ever hear about false alarms, never about
  misses.

> what does called too low vs high mean

● They compare the judge's level with the clinician's. The levels run No →
  Routine → Urgent.

  - Called too low means the judge picked a lower level than the clinician.
    Example: the clinician said Urgent and the judge said Routine or No. These
    are missed cases: someone who needed a human might not get one. This is the
    dangerous kind of mistake.
  - Called too high means the judge picked a higher level than the clinician.
    Example: the clinician said No and the judge said Routine. These are false
    alarms: staff spend time on something that didn't need them. That's annoying
    but safe.

  So v1 missing about 9 cases per run was the serious problem, and v2 brings
  that to 0.
