> isnt it better to enforce 1 email per person for simplicity. all this data
  was manually maintained. if we create a platform for it wouldnt it be more
  correct to enforce 1 email

● Yes, that's reasonable. For a platform you're designing, one email per person
  is the right call. The second email table was really solving a data-cleaning
  problem, not a product requirement. Jonas has two emails because the old
  process used separate forms that didn't check identity. On a platform where he
  logs in, he'd use one account, and his attendance would attach to his person
  record, not to whatever email he typed.

  There are two refinements I'd still keep.

  1. Keep a surrogate person_id as the primary key, with email as a unique
  column, not the PK.
  person
    person_id   PK
    email       UNIQUE NOT NULL (stored lowercased / case-insensitive)
    ...
  This doesn't add complexity, it just keeps the model safe:
  - People change emails (job changes, as with orgalpha vs mailbox). With email
    as the PK, a change spreads to every foreign key in attendance,
    applications, payments and so on. With a surrogate key, it's a one-column
    update.
  - The case problem (Priya.Nair vs priya.nair) is handled once, by a unique
    constraint that ignores case.

  2. Resolve the old duplicates during migration, not in the schema.
  The import script needs a one-off mapping: jfeld88@mailbox.example → Jonas's
  person. Keep that mapping in the migration code, or a throwaway lookup table,
  and don't add it to the model. The same goes for the Wise rows with no email
  ("MD Noor R."): match them to a person by hand once, and store the result as a
  normal person_id foreign key.

  What it changes in the earlier model: drop person_email and add email to
  person. Everything else stays: application, membership, attendance, all
  hanging off person_id.

  One thing to decide ahead of time: Stripe and Wise will send payer emails that
  may not match the account email, for example when a parent or employer pays
  (Mateo's employer). Link payments through application_id, or through Stripe
  metadata, rather than matching on email. Then the one-email rule never has to
  cover payers.

> why allow duplicate applications. just make person id and cohort id a
  composite key

● Agreed. Duplicate applications are a data-quality accident, not something to
  model, so add the constraint and drop duplicate_of. My one tweak: make it a
  unique constraint, not the primary key.

  application
    application_id   PK          -- keep RW26-018 style IDs
    person_id        FK -> person
    cohort_id        FK -> cohort
    ...
    UNIQUE (person_id, cohort_id)

  Why not a composite PK:
  - Other tables reference the application. Group membership, the deposit and
    payments would each need both person_id and cohort_id as foreign keys. A
    single application_id is simpler to join and to pass around in URLs, Stripe
    metadata and so on.
  - The organization already has an ID for it. RW26-018 is the reference staff
    use and that shows up in communications. Throwing it away to use a composite
    key would lose that.
  - You get the same guarantee. UNIQUE (person_id, cohort_id) blocks duplicates
    exactly as a composite PK would.

  Consequences to think through:
  - Re-applying in the same cohort becomes an update, not a new row. If someone
    declines and changes their mind, or moves from the waiting list into a
    group, you change the existing application's status. If you want that
    history, add an application_status_history table (application_id, status,
    changed_at) instead of creating new applications.
  - Applying to a different cohort is still allowed. Emily's RW25-112 (2025
    Fall) and RW26-012 (2026 Summer) are both valid.
  - For the migration, Daniel's RW26-027 gets merged or dropped. RW26-003 is the
    real application (Program Completed, Group 81, deposit refunded). RW26-027

● The file contains more than deposits, and that changes the model:

  - Two kinds of payment. There's the refundable motivational deposit ($50 /
    $200), and a separate program contribution that looks like pay-what-you-can
    ($30–$150) and is never refunded. Most people paid both, two minutes apart.
  - The payer isn't always the participant. Mateo's contribution was paid by
    finance@orggamma.example / "OrgGamma Ltd".
  - Refunds are recorded two ways. Stripe marks the original charge (Amount
    Refunded, Status=Refunded); Wise adds a separate negative row.
  - Failed attempts are included. Sofia's first $200 charge failed and she
    retried.
  - Payments don't always map cleanly to one purpose. Tomas paid one €212 "CBT
    Lab" charge, in a different currency, not split into deposit and
    contribution.
  - Some charges have no matching application. Marta Kowal paid a $200 deposit
    and isn't in applications.csv.

  Suggested schema

  payment                              -- one row per money movement
    payment_id       PK
    provider         enum: stripe | wise | paypal
    provider_ref     UNIQUE (ch_SYN..., WISE-...)
    application_id   FK -> application, NULLABLE (null = unmatched, e.g. Marta)
    kind             enum: charge | refund
    refund_of        FK -> payment, nullable (refund -> original charge)
    purpose          enum: deposit | contribution | unallocated
    amount_minor     int (cents), always positive; kind gives direction
    currency         char(3)
    fee_minor        int, nullable
    status           enum: succeeded | failed | pending
    created_at       timestamptz
    payer_name       snapshot from provider (OrgGamma Ltd)
    payer_email      snapshot from provider, not FK to person

  deposit                              -- the commitment, one per application
    application_id   PK, FK -> application
    amount_minor     int (50 / 200 tier)
    currency
    outcome          enum: pending | refunded | forfeited | donated | waived
    decided_at       timestamptz, nullable

  Reasoning behind the main choices

  - Refunds are their own rows, linked by refund_of. Stripe and Wise end up in
    the same shape. During migration, a Stripe charge with Amount Refunded > 0
    becomes a charge row plus a refund row. "Net paid" is then just a sum.
  - Payments link to the application, not to the person. This is the earlier
    point about payers: Emily's 2025 and 2026 deposits attach to different
    applications, and the employer payment attaches to Mateo's application
    without OrgGamma's email polluting person.
  - Payer details are a snapshot. It's what Stripe or Wise reported, kept for
    reconciliation. No payer entity is needed.
  - deposit holds the decision, payment holds the money. The application's
    "Motivational Deposit Status" becomes deposit.outcome. "Not Met" is
    forfeited, and "Not Applicable" means no deposit row, or waived for Mateo.
    Comparing the outcome with the actual payments is how you'd catch the
    inconsistencies below.
  - Failed charges stay as status=failed. They're useful for the audit trail,
    and you leave them out of totals.
  - Store amounts in minor units with a currency column. That deals with Tomas's
    EUR payment, and avoids float rounding.

  One decision to make: if combined payments like Tomas's €212 are rare, purpose
  = unallocated plus a manual note is enough. If they're common, add a
  payment_allocation(payment_id, purpose, amount_minor) table so one charge can
  be split. I'd start without it.

> schema for attendance

● This is the attendance part of task1/schema.sql: session, group_membership,
  attendance, and a view for totals.

  -- One meeting of one group.
  CREATE TABLE session (
      session_id      BIGSERIAL PRIMARY KEY,
      group_id        BIGINT NOT NULL REFERENCES "group" (group_id),
      session_number  INT NOT NULL CHECK (session_number BETWEEN 1 AND 12),
      held_on         DATE,
      UNIQUE (group_id, session_number)
  );

  -- One stint in one group. A move (e.g. G82 -> G83) is two rows.
  CREATE TYPE membership_end_reason AS ENUM ('moved', 'dropped');

  CREATE TABLE group_membership (
      membership_id   BIGSERIAL PRIMARY KEY,
      application_id  TEXT NOT NULL REFERENCES application (application_id),
      group_id        BIGINT NOT NULL REFERENCES "group" (group_id),
      start_session   INT,
      end_session     INT,
      end_reason      membership_end_reason,
      CHECK (end_reason IS NULL OR end_session IS NOT NULL)
  );

  -- One row per member per session they were expected at.
  CREATE TABLE attendance (
      membership_id  BIGINT NOT NULL REFERENCES group_membership
  (membership_id),
      session_id     BIGINT NOT NULL REFERENCES session (session_id),
      presence       NUMERIC(2, 1) NOT NULL CHECK (presence IN (0, 0.5, 1)),
      PRIMARY KEY (membership_id, session_id)
  );

  -- Totals per application, summed across group moves.
  CREATE VIEW application_attendance AS
  SELECT gm.application_id,
         SUM(a.presence)             AS sessions_attended,
         COUNT(*)                    AS sessions_recorded,
         SUM(a.presence) / COUNT(*)  AS attendance_rate
  FROM attendance a
  JOIN group_membership gm USING (membership_id)
  GROUP BY gm.application_id;

> how do we design the schema such that it allows participants to change group

● The schema already supports moves: a move closes one group_membership row and
  opens another on the same application. The current DDL just doesn't stop
  invalid moves. Here's the complete design with the constraints that make it
  reliable.

  How a move works

  Hannah moves from G82 to G83 starting week 3, in one transaction:

  What changed:
  - One group at a time. group_membership has an exclusion constraint, so a
    person's week ranges can't overlap. A current membership (no end week yet)
    counts as open-ended, so you can't open G83 until G82 is closed. This needs
    the btree_gist extension, which is now created at the top of the file.
  - Same cohort. Memberships now carry cohort_id, with two composite foreign
    keys, so the group has to be in the application's cohort.
  - Own group's sessions only. Attendance now carries group_id, with composite
    foreign keys to both the membership and the session, so a session from
    another group is rejected.
  - Only the member's weeks. A trigger rejects attendance for a week outside the
    membership's range.
  - Clearer week rules. start_week is now required (default 1), end_week can't
    be before start_week, and end_reason is set exactly when end_week is. A
    participant who finishes normally keeps end_week = NULL.

  Gaps:
  - The trigger only checks attendance when it's inserted or updated. If you
    later shorten a membership's week range, existing attendance outside the new
    range isn't caught. To cover that, add a second trigger on
    group_membership, or never edit ranges after attendance has been recorded.
  - Why someone moved isn't recorded. end_reason = moved says what happened, not
    why (Hannah's "schedule clash"). If you want that for reporting, add a
    change_reason enum (e.g. schedule_clash, group_fit, facilitator_request),
    not free text.
  - The attendance view hasn't changed. It still divides by sessions recorded.
    Using "sessions that happened during the member's weeks" as the denominator,
    as we discussed, is a separate change.

> explain diff statuses of deposit

● In the schema, the deposit's status is deposit.outcome, which can be one of
  five values. There's also a sixth case: no deposit row at all.

  Outcome: pending
  Meaning: Deposit paid, no decision yet. Either the programme is still running,

  or it has ended and nobody has processed the refund.
  CSV status it comes from: Pending
  Example: Priya (completed, qualifies, not yet refunded); Isabel (depends on
  week 12 attendance)
  ────────────────────────────────────────
  Outcome: refunded
  Meaning: Participant met the rules and got the deposit back
  CSV status it comes from: Refunded
  Example: Anneke, Noor
  ────────────────────────────────────────
  Outcome: forfeited
  Meaning: Participant didn't meet the rules, so the organization keeps the
  deposit
  CSV status it comes from: Not Met
  Example: Daniel Okoro (7/9 sessions)
  ────────────────────────────────────────
  Outcome: donated
  Meaning: Participant met the rules, or would have, but chose to leave the
  deposit as a donation
  CSV status it comes from: Donated
  Example: Aisha ("wants to donate deposit")
  ────────────────────────────────────────
  Outcome: waived
  Meaning: A deposit applied, but the organization dropped the requirement
  CSV status it comes from: none yet
  Example: (unused, see below)
  ────────────────────────────────────────
  Outcome: no row
  Meaning: No deposit ever applied
  CSV status it comes from: Not Applicable
  Example: Lucia (waiting list), Peter (declined)

  Lifecycle

              placed in a group, deposit paid
                          │
                       pending
            ┌─────────────┼──────────────┐
     meets rules     meets rules,    misses rules
            │       chooses to donate     │
        refunded        donated        forfeited

  - Only pending can change. The other outcomes are final, and decided_at
    records when the decision was made.
  - refunded should always have a matching refund payment row. That pairing is
    what caught Ben, who is marked refunded but has no refund payment. Greta is
    the opposite case: she has a refund payment but is still pending.
  - forfeited and donated both mean the organization keeps the money, but for
    different reasons. Keep them separate for reporting: donated money is a
    gift, forfeited money is a missed commitment.

  About waived

  The loader doesn't use it at the moment. Mateo's "employer pays" was Not
  Applicable, so he gets no deposit row. Use waived for a different case: a
  participant who would normally owe a deposit but is excused from it, such as a
  hardship exception or a staff decision. That separates "this person never
  needed a deposit" (no row) from "this person was excused from one" (waived).
  If you'd rather keep it simple, drop waived and use no row for both.

  scale. The three score columns are phrased as statements to agree or disagree
  with ("The session today was engaging for me", "The facilitator's behavior
  supported the session optimally", "I felt seen, supported, and affirmed").
  That's the usual format for a 7-point Likert scale, from 1 = strongly disagree
  to 7 = strongly agree.

  The values in the file fit that:

  ┌───────────────────────────────────┬─────────────┐
  │               Item                │ Values seen │
  ├───────────────────────────────────┼─────────────┤

> wouldnt it be better to use an enum for payment type - deposit or

● Yes, and the database already does that. payment.purpose is an enum (CHECK
  (purpose IN ('combined', 'deposit', 'contribution'))), and the refund logic
  reads only that column.

  The only place that reads the description is load_db.py (task1/load_db.py),
  during the import. payments.csv has no payment-type field, so the loader has
  to infer the enum value once from the text ("motivational deposit", "program
  contribution", "MD ..."). After that, nothing looks at the description again.

  That's why it appears in FINDINGS.MD: the fix belongs at the source, so the
  type exists when the payment is made:
  - Stripe: use separate products for the deposit and the contribution, or add
    payment_type=deposit to the payment's metadata. The export then has a real
    column and the loader can map it directly.
  - Wise rows typed by hand: add a required "Type" column with the same two
    values.

  Once the sources provide it, the guessing in load_db.py can be deleted.

  There's one decision to make about combined. It exists because your rules say
  "each participant makes one payment" covering both, as with Tomas's single
  €212 charge. If you switch to two separate payments, as most participants
  already make, you can drop combined and keep just deposit / contribution. If
  you keep the one-payment process, combined stays, and you'd also need to
  record the deposit share (e.g. via deposit.amount_minor), which the schema
  already does.
